# ADR-004: MicroTensor Schema (18-D)

- **Status:** Accepted
- **Date:** 2026-09-24
- **Related:** ADR-001, ADR-005, ADR-006

## 1. Context

The MicroTensor is the shared representation between browser runtime and offline training.
It is `18`-D: nine normalised features followed by nine modality capability masks, so that a
missing modality is *represented as missing* rather than imputed as a synthetic zero.

The canonical definition lives in `model-preparation/src/config.yaml`
(`preprocessing.num_features: 9`, `preprocessing.input_dim: 18`), propagated by
`npm run sync-config` into `src/config/pipelineConfig.json`. The TypeScript accessor is
`src/config/pipelineConfig.ts`; the runtime writer is `src/microtensor/features.ts`.

## 2. Problem

The `18`-D layout is now embedded in the Python preprocessing pipeline, the exported ONNX graph,
the browser runtime, the parity fixtures and the trace schema. Any change is a cross-repository,
model-invalidating change. The plan adds a `TargetInterventionHead` and a dataset pipeline, so
the question is whether the schema can stay fixed while those land.

## 3. Options considered

| Option | Change |
| --- | --- |
| **A. Freeze at 18-D** | No schema change; new work consumes the existing tensor. |
| **B. Extend features** | Add contextual or derived features; input dim grows beyond 18. |
| **C. Add self-describing metadata beside the tensor** | Keep 18-D, but ship feature-name/version metadata alongside windows and datasets. |

## 4. Evidence available

**Verified by automated test**

- `npm run parity:check` compares TypeScript output against the Python reference
  (`scripts/regenerate-parity-fixture.mjs --check`, `tests/parity.test.ts`).
- `tests/microtensor_features.test.ts` (8 tests) and `tests/microtensor_window.test.ts`
  (4 tests) pass.
- `src/microtensor/schema.ts` declares the schema and version consumed by the trace.

**Known limitations carried forward**

- `dwellTimeMs` is a **proxy**: both implementations derive it from a qualifying-event count
  (`count × 40 ms`), not measured hover duration. Parity holds; construct validity is
  unestablished (`target-testbed-implementation-record.md` §4.4).
- The parity fixtures are static JSON; provenance that they were generated by the Python
  reference is *inferred, not proven by an artifact* (`target-testbed-quality-assessment.md`
  §27).

## 5. Decision required

Whether the schema stays frozen at 18-D for the intervention-head milestone, and whether a
provenance fix is required now.

## 6. Recommended option

**Option A — freeze at 18-D — plus the Option C provenance addition, which does not change the
tensor.** The intervention head consumes `h_T` (64-D latent) concatenated with `UIContext`
(6-D); it does not need new MicroTensor features. Adding features now would invalidate the
foundation model, the exported graph and the fixtures for no demonstrated gain.

**Do not change `dwellTimeMs` semantics in this plan.** The runtime and Python sides currently
agree; changing the derivation on one side only would break parity, and changing both would
invalidate the foundation checkpoint. It is recorded as a construct-validity limitation and
deferred.

## 7. Consequences

- `TargetInterventionHead` integration does not require re-exporting the foundation graph's
  input contract; `18`-D input and `7`-class outcome output stay valid.
- A separate, versioned intervention-head graph is exported (ADR-006), so the foundation graph
  remains usable for outcome diagnostics and ablation.
- Any future feature addition becomes an explicit schema-version bump with a new parity fixture
  set and a re-trained foundation model. This is the deliberate cost of freezing now.

## 8. What is being deferred

> **Decision:** Feature-set extension and `dwellTimeMs` construct validity.
> **Deferred until:** After the intervention-head experiment runs end to end.
> **Reason:** Both invalidate the foundation checkpoint and the exported graph; neither is
> required for the immediate milestone.
> **Current workaround:** The nine features are fixed and documented; `dwellTimeMs` is labelled a
> proxy in the implementation record.
> **Risk:** Medium for research validity — a proxy feature may correlate with event density
> rather than dwell. Low for engineering — parity is enforced.
> **Evidence required to revisit:** A measured correlation between the `dwellTimeMs` proxy and
> independently measured hover duration on real traces.

> **Decision:** Regenerating parity fixtures from the Python reference inside CI.
> **Deferred until:** Plan 1 task 6.3 (provenance-versioned manifest and trace validators).
> **Reason:** The fixture provenance gap is real but is not on the critical path to the
> intervention-head milestone.
> **Current workaround:** `npm run parity:check` compares against checked-in JSON.
> **Risk:** Medium — a stale fixture would silently pass.

## 9. Conditions that would force this decision to be revisited

- The intervention head fails to reach usable confidence and the diagnosis points at missing
  input signal rather than training data volume.
- A target UI integration cannot supply one of the nine modalities and needs a schema change to
  represent that honestly.
- The parity provenance gap is found to have already produced a false pass.
