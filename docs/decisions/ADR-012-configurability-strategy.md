# ADR-012: Configurability Strategy

- **Status:** Proposed — decision required
- **Date:** 2026-09-24
- **Related:** ADR-004, ADR-005, ADR-006, ADR-011

## 1. Context

The brief (§7) makes configurability a core architectural requirement, naming nine parameter
groups that must not be hard-coded: telemetry, windowing, MicroTensor, macro sequences, Fast
Gate, Slow Gate, policy, actuation and experiment. It requires sensible defaults so another UI
does not need a large configuration file merely to start collecting telemetry.

Today there are **two** configuration sources with a one-way sync:

1. `model-preparation/src/config.yaml` — declared the single source of truth in `AGENTS.md` §5.
2. `edge-aui-framework/src/config/pipelineConfig.json` — generated by
   `npm run sync-config` (`scripts/sync-config.mjs`), exposed through the typed accessor
   `src/config/pipelineConfig.ts`, and asserted against by `tests/sync_config.test.ts`.

Runtime tuning values that are *not* in `config.yaml` currently live as literals in
`adaptiveRuntime.ts` and the policy/gate constructors.

## 2. Problem

The sync is one-directional and covers only preprocessing, target-generation, training and export
fields. Everything that is a *runtime experiment* parameter — window minimum events, settlement
delay, policy thresholds, cooldowns, TTLs, gate support and confidence thresholds, model paths,
sequence length, batch size, experiment and condition identity — has no single home. A
researcher tuning an ablation currently edits source.

Two further defects sit here:

- `tests/sync_config.test.ts` writes `src/config/pipelineConfig.json` during `npm test`; the
  helper supports an `outputPath`, so this is avoidable.
- If runtime parameters are added to `config.yaml` and synced, an *unsynced edit* becomes a new
  class of silent misconfiguration.

## 3. Options considered

| Option | Description |
| --- | --- |
| **A. One `config.yaml`, fully synced** | Extend `config.yaml` with runtime sections; sync everything into the JSON. |
| **B. Two layers: shared schema + runtime override** | `config.yaml` owns shared/model fields; a separate runtime config owns experiment knobs, with the model fields still synced. |
| **C. Runtime-only JSON** | Move all configuration into the framework; drop the sync. |
| **D. Config objects in code with defaults** | Typed defaults, overridable programmatically; no file. |

## 4. Evidence available

**Verified**

- `npm run sync-config` and `tests/sync_config.test.ts` exist and pass.
- `PIPELINE_CONFIG` is typed and consumed by the runtime (ADR-004).
- `npm run parity:check` depends on the synced values staying consistent with Python.

**Observed**

- The Python side reads the same `config.yaml`, so any field placed there must remain meaningful
  to Python. Experiment-only knobs (cooldowns, TTLs) have no Python meaning.

**Not measured**

- How many distinct configuration values the runtime currently hard-codes. `NOT MEASURED`
  (needed to size the work in plan 1 task 4.2).

## 5. Decision required

Whether there is one configuration source or two layered ones, and which agent owns the shared
schema.

## 6. Recommended option

**Option B — two layers, with an explicit shared schema.**

- `model-preparation/src/config.yaml` remains the single source of truth for anything both sides
  must agree on: windowing, feature order, scale constants, outcome taxonomy, intervention
  vocabulary, model and export metadata. `npm run sync-config` continues to generate the
  framework's typed view of these.
- A **framework-owned runtime configuration** (with typed defaults in code) owns experiment-only
  knobs: policy thresholds, cooldown, TTL, dismissal, settlement delay, experiment/condition
  identity, trace schema version.

Rationale: forcing experiment knobs into `config.yaml` would either pollute the Python pipeline's
schema with fields it cannot interpret, or require Python to carry validation for values it never
reads. Layering keeps the sync honest and keeps the shared schema meaningful.

**Non-negotiable sub-decision:** every configuration group named in brief §7 must be settable
without editing runtime source, and defaults must be sufficient to start collecting telemetry.
This is the acceptance criterion for plan 1 task 4.2.

## 7. Consequences

- Two configuration files exist, so the documentation must state unambiguously which layer a
  given parameter belongs to. Ambiguity here recreates the problem being solved.
- A configuration value whose change would invalidate a model (feature order, scale constants)
  must remain in the synced layer and carry a version.
- `sync_config.test.ts` must be made hermetic (write to a temp path) so the shared layer can be
  validated without mutating a tracked file.

## 8. What is being deferred

> **Decision:** Whether the framework should support runtime configuration hot-reload or a
> config UI.
> **Deferred until:** The configurability refactor lands and its ergonomics are observed in use.
> **Reason:** Hot-reload is a convenience, not a requirement, and it interacts badly with the
> reproducibility guarantee (a trace must record the configuration that produced it).
> **Current workaround:** Restart with a different configuration; the configuration is recorded
> in the trace.
> **Risk:** Low.
> **Evidence required to revisit:** Reported friction during ablation runs.

> **Decision:** Making `sync_config.test.ts` hermetic.
> **Deferred until:** Plan 1 task 4.2, where the sync script is already being touched.
> **Reason:** Measured idempotent today; not isolated. Touching it separately would churn a test
> file twice.

## 9. Conditions that would force this decision to be revisited

- A second UI needs a configuration surface that the layered model cannot express.
- The reproducibility requirement is found to be violated because a parameter was read from
  somewhere the trace does not record.
- Python needs to consume a parameter currently in the runtime layer.
