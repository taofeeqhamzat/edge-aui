# Task 60.1 — Outcome Policy and Target Resolution

## Description

Implement the testbed's semantic outcome→intervention policy and the target-resolution contract:

- map predicted outcomes + UI context to candidate interventions;
- keep the generic policy gates (confidence, persistence, context, cooldown, dismissal, TTL,
  per-task limit);
- resolve targets through the application resolver;
- define missing-target behavior and record actuation failure.

## Acceptance criteria

- [x] A testbed policy maps the approved semantic outcomes to candidate interventions; unmapped/
      ambiguous outcomes fall back to `no_op`. The map lives in
      `src/testbed/config/policyAdapter.ts`: filter-selection outcomes simplify the options,
      committing outcomes highlight the primary action, `inspect_help` expands the inspected
      tooltip, and `select_region`, `reset_filter`, `close_filter_section`, the navigation
      outcomes and `NO_OUTCOME` record a decision-only verdict.
- [x] Confidence/context/cooldown/dismissal/TTL/limits remain enforced; repeated predictions do not
      produce repeated interventions. The policy refuses a candidate whose accepted adaptation
      already answers the current observed act (`rejectionCategory: 'already_adapted'`) and the
      runtime re-arms it on each new macro interaction. Found live: before this, an idle
      participant was re-adapted every cooldown period from one act (see the verification report
      §7, §8.6).
- [x] The `simplify_options` target is supplied by configuration, not hardcoded in framework core.
      `src/testbed/config/interventionTargets.ts` declares `filter-options`; the framework only
      accepts a resolver.
- [x] Missing target → no mutation, explicit actuation failure and policy record. The actuator
      refuses an actionable command with no declared target, and a declared target that does not
      resolve (or resolves to an element that cannot accept the adaptation) returns `false`; the
      runtime records `phase: 'actuation_failed'`, `rejectionCategory: 'actuation_failed'`.
- [x] Baseline condition remains decision-only and never applies an adaptation. Asserted through
      the composed runtime in `tests/policy_adapter_wiring.test.ts`.
- [x] `expand_tooltip` uses real title/data-tooltip text; no generic fallback target. The bubble
      text is the target's own `title`/`data-tooltip`; a target without one is refused, and the
      first-tooltip fallback is removed.
- [x] Tests cover mapping, conservative suppression, cooldown/TTL, missing target and baseline.
      `tests/testbed_intervention_targets.test.ts` (19 tests), `tests/policy_cooldown_ttl.test.ts`
      (4 repeat-suppression tests), `tests/intervention_verification.test.tsx` (11 tests),
      `tests/policy_adapter_wiring.test.ts` (6 tests), plus the updated
      `tests/actuator.test.ts` and `tests/trace_schema_1_4.test.ts`.
- [x] `npm test` and `npm run typecheck` pass (661 of 668 tests; the 7 failures are the
      pre-existing `.env.local` environment failure in `tests/experiment_condition.test.ts`,
      reproduced at commit `3cec83f`).

## Notes

- A predicted action does not always justify assistance; default to `no_op`.
- Keep the policy mapping out of framework core.
- Do not claim user benefit from a model prediction; this task verifies mechanism, not usefulness.

## Implementation notes

- The policy mapping was added to the existing `src/testbed/config/policyAdapter.ts` rather
  than a new `src/testbed/policy/outcomePolicy.ts`. The adapter already *is* the testbed's
  outcome→candidate decision and is imported by the composition root; moving it would have
  churned imports without changing the boundary.
- Targets are resolved by the application (`createTestbedTargetResolver`) and supplied to the
  runtime through `registerRuntimeDefaults({ targetResolver })`. The runtime and framework
  core hold no component id.
- The adaptation target never comes from `context.activeComponentId`; that fallback was
  removed. A prediction that names an element (an inspected tooltip) supplies its own target,
  and the resolver validates it.
- `InterventionPolicy` gained one gate, ordered after the cooldown/dismissal checks: one
  accepted adaptation answers one observed act. `PolicyRejectionCategory` gained
  `already_adapted`; the name is documented in `docs/data_schemas.md`.
- Rejections are recorded for every outcome of the decision chain, including the refusal
  paths this task added, so a trace can still answer "why did it not intervene?".
